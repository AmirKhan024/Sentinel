Sentinel Feature Pipeline Audit — Read-Only Verification
Scope: src/sentinel/features/ (Component 4), cross-checked against src/sentinel/modeling/ (Component 6), src/sentinel/boosting/ (Component 7), src/sentinel/neural/ (Component 8, experimental), src/sentinel/entity/ (Component 2), src/sentinel/evaluation/rankers.py (Component 5), and docs/decisions/*.md / docs/data_contracts/as_of_features.md. All findings below are grounded in files actually read; nothing is inferred from naming alone.

1. The real feature-building pipeline and every feature it computes
Source of truth: src/sentinel/features/definitions.py — FEATURE_SPECS: tuple[FeatureSpec, ...] (declared at definitions.py:80-339, extended by _window_specs() at definitions.py:342-384). FEATURE_COLUMNS (definitions.py:387) is described in code comments as "the only columns a model may consume," and is enforced downstream (see §3).

Orchestrator: src/sentinel/features/build.py::build_features (build.py:70-197) reads three upstream artifacts (raw Parquet snapshot, Component 2 establishment assignments, Component 3 targets), calls historical.priority_flags then historical.compute_features, then writer.finalize.

Actual SQL/computation: src/sentinel/features/historical.py. The entire aggregation is one DuckDB query built by aggregate_sql() (historical.py:163-231), joined via:


FROM targets t
LEFT JOIN history h
  ON  h.establishment_id = t.establishment_id
  AND h.inspection_date  <  t.inspection_date   -- THE temporal boundary
(historical.py:224-227). features_sql() (historical.py:234-307) then derives the final columns and applies the null rules. compute_features() (historical.py:310-323) runs HISTORY_SQL → TARGETS_SQL → aggregate_sql() → features_sql() in sequence and returns rows sorted by (establishment_id, inspection_date, target_inspection_id).

Total: 26 features (20 base + 3 windows × 2 paired columns), confirmed by MODEL_REGISTRY's logistic_regression description at modeling/definitions.py:163 ("all 26 as-of features") and by BoostingSpec description at boosting/definitions.py:310 ("all 26 as-of features"). All are establishment-level temporal features (no spatial features — see §2). Below, source table = raw (the ingested Chicago food-inspection snapshot) joined to assignments (Component 2 entity resolution) and target_rows (Component 3) unless noted.

As-of correctness (structural guarantee)
Every single feature is computed from one GROUP BY over the range join above, so every feature in this table is, by construction, filtered to history.inspection_date < target.inspection_date before any aggregation happens — there is exactly one join, so there is exactly one place the cutoff could be wrong, and it is applied once for all 26 columns (historical.py:224-227, confirmed in the module docstring at historical.py:1-36 explaining why this is a single range join rather than a groupby-then-merge, which the docstring calls "the classic all-history bug"). This is VERIFIED BY CODE, not merely documented — historical.py re-derives the same boundary in validate.py independently (per the docstring, not separately verified line-by-line here but referenced structurally).

Demographic/community-area features
No demographic variable (race/income/ACS/census) exists anywhere — verified by grep across the whole tree (no hits) and explicitly stated in ADR 0023 and BLOCKED_EXPERIMENTS in neural/build.py:196 ("demographic features: no race, income or ACS variable is used anywhere"). Community area exists only as the experimental categorical embedding described above (Component 8, Category.COMMUNITY_AREA, neural/definitions.py:92), explicitly audited in ADR 0023 as "a possible demographic proxy," with a declared-in-advance non-retention rule ("a better score does not retain it") and a matched ablation neural_no_community_area (neural/definitions.py:371). This is real code, but it is experimental, non-production, and not part of the feature pipeline audited in §1.

Inspector-identity-related features or inspector random-effects marginalization
NOT FOUND anywhere, and the codebase asserts it cannot exist on this data. ADR 0019 (docs/decisions/0019-inspector-effect-modelling-is-blocked.md) is unambiguous: the ingested Socrata dataset (4ijn-s7e5) publishes 22 columns and "None identifies a person." modeling/definitions.py:73 and evaluation/rankers.py:32 both list inspector identity as unreachable/excluded. There is a regression test named in the ADR, tests/test_boosting_inspector_blocked.py (not independently re-verified line-by-line here, but its existence and purpose is stated in the ADR and its function is to fail if an inspector-like column ever appears). DOCUMENTED-ONLY-NOT-FOUND-IN-CODE, and the documentation is fully consistent with the code (both say it's absent/blocked).

Component 6 (baseline logistic regression), src/sentinel/modeling/definitions.py:

MODEL_REGISTRY[0] logistic_regression: feature_columns=FEATURE_COLUMNS (modeling/definitions.py:167) — all 26 Component-4 features, no exclusions.
logistic_regression_no_scheduling: all 26 minus days_since_any_inspection (ABLATED_FEATURE, modeling/definitions.py:108,154-155,182) — a deliberate ablation, not an unused/forgotten feature.
cdph_2015_approximation: restricted to Family.CANVASS_HISTORY, PRIORITY_HISTORY, WINDOW, OBSERVATION via _cdph_feature_columns() (modeling/definitions.py:98-103,149-151) — deliberately excludes Family.CONTEXT and Family.TENANT to approximate the 2015 model's reachable input families; documented as an approximation, not a full replication (CDPH_APPROXIMATION_NOTE, modeling/definitions.py:81-90).
An import-time guard _guard_registry() (modeling/definitions.py:313-354) raises if any registered model names a column outside FEATURE_COLUMNS or inside FORBIDDEN_COLUMNS (identity/label/provenance columns) — so it is structurally impossible for a model spec to smuggle in an unlisted feature.
Component 7 (boosting), src/sentinel/boosting/definitions.py: xgboost and lightgbm both use feature_columns=FEATURE_COLUMNS (all 26) (boosting/definitions.py:315,328); xgboost_class_weighted is a class-weighting ablation with the same 26 columns (boosting/definitions.py:342). Same guard pattern (boosting/definitions.py:423-489) enforces closure against FEATURE_COLUMNS/FORBIDDEN_COLUMNS.

Defined-but-unused features: none found within the 26-column Component-4 contract. Every one of the 26 FEATURE_SPECS columns is consumed by at least logistic_regression/xgboost/lightgbm (the "all-26" models); the only exclusions are the two declared ablations above (ABLATED_FEATURE, and the CDPH-family restriction), both intentional and documented, not orphaned definitions. There is no feature present in FEATURE_SPECS that no registered model ever references.

Component 8 (neural, experimental) uses features Components 4/6/7 do not: chain_key, facility_type, community_area, zip categorical embeddings (neural/definitions.py:90-93) plus (per neural/definitions.py:294-295) the same 26 standardized Component-4 features concatenated with the embeddings. These extra categorical inputs are not part of FEATURE_COLUMNS/feature_definition_version and are explicitly kept out of Components 4/6/7 by ADR 0022/0023 ("Component 8's categoricals are an experimental layer"). This is the one place features exist that are used by "a model" but not by the production feature contract.

4. Explicit leakage guards in this code
As-of temporal cutoff (structural, single-join guarantee). historical.py:224-227 — h.inspection_date < t.inspection_date, applied once for every one of the 26 features via a single LEFT JOIN + GROUP BY (aggregate_sql(), historical.py:163-231). The module docstring (historical.py:16-26) explicitly rules out <= (documented same-day-ordering bug risk) and rules out groupby-then-merge (attaches future information to past rows). build.py:43 records the same boundary string in the manifest (TEMPORAL_BOUNDARY) so it travels with the artifact.
Priority-flag consistency guard. historical.py:62-108 priority_flags() reuses Component 3's own violation parser (sentinel.target.violations.parse_violations) rather than an independent SQL heuristic, specifically "so 'priority' cannot mean one thing in the label and another in the feature" (historical.py:31-36) — a label/feature-drift leakage guard, not a temporal one.
Registry-level column-closure guard against forbidden columns. modeling/definitions.py:313-354 _guard_registry() (Component 6) and boosting/definitions.py:423-489 _guard_registry() (Component 7): both raise (not assert, deliberately, since assert is stripped under -O) if any registered model's feature_columns intersects FORBIDDEN_COLUMNS = {establishment_id, inspection_date, target_inspection_id, target, target_status, code_era_phase, feature_definition_version} (modeling/definitions.py:64), or references a column absent from FEATURE_COLUMNS.
Preprocessing/imputation leakage guard (train-only statistics). modeling/build.py:20-22 module docstring states determinism/no-leakage rests on "Preprocessing statistics come only from the training window," and MissingStrategy.MEDIAN is described as "Train-window median. Partition-based, so exactly order-invariant" (modeling/definitions.py:116-117). (I did not independently trace preprocess.py's implementation line-by-line in this pass, but the fold-partitioned design is stated as a hard property in the orchestrator docstring and reflected in _load/_build_folds/train.fit_fold structure at modeling/build.py:136-157.)
Fold-set separation for hyperparameter tuning (temporal leakage guard for tuning, Component 7). boosting/definitions.py:210-214,375-395: two separate Optuna studies (quarterly, covid_shift) because "the quarterly tuning region contains the covid_shift test window: one shared study would make the shift result optimistically biased" — tuned_params() raises KeyError rather than silently falling back to a default or borrowing across fold sets (boosting/definitions.py:375-395).
No leave-one-out or target-encoded features found anywhere in features/. I found no chain-violation-rate target encoding, no leave-one-out encoding, and no target-mean encoding of any kind in src/sentinel/features/, src/sentinel/modeling/, or src/sentinel/boosting/ (grep for "leave_one_out"/"leave.one.out"/"target.encod" across the codebase returned zero hits anywhere, not just in these directories). The only rate-like feature is prior_canvass_fail_rate / prior_canvass_priority_rate, both establishment-own-history ratios computed under the as-of boundary (§1), not encodings of the target against other establishments' outcomes, so there is no leave-one-out concern to guard against in the first place. This is a case where the user's premise (that a chain-violation-rate target-encoded feature exists) does not match the code: no such feature exists. DOCUMENTED-ONLY-NOT-FOUND: not even mentioned in docs as implemented; ADR 0021 (entity-embeddings-and-the-forbidden-columns-guard, referenced at neural/build.py:186-188) discusses guarding against an establishment_id embedding as a leakage surface in the experimental neural component, which is the closest related leakage guard, but it concerns entity-identity embeddings, not target encoding of chain violation rates.

Sentinel Component 14 Scheduling Audit — "All 28 establishments on April 1" anomaly
Executive summary
This is not a code bug. It is the mathematically correct output of the horizon rule for k_name="k_1_day", combined with a genuine semantic conflation in the frontend copy between "the fold being evaluated" (a 3‑month evaluation window) and "the schedule's horizon" (the number of operating days the requested capacity k actually spans). Verified with real data from the repo's own manifest and parquet artifacts — the exact case in the report (fold_id="quarterly-2026Q2", k_name="k_1_day", 28 establishments, single date 2026-04-01) is reproduced verbatim from data/processed/scheduling/schedule_summary_20260826T131416Z.parquet. Worse than an edge case: this is literally the default scope a fresh visitor sees (see §5), because useDefaultScope auto-selects the latest quarterly fold and the manifest's primary_k_level, which is "k_1_day".

1. Capacity model
File: src/sentinel/scheduling/definitions.py, class CapacityMode (lines 94–111), DEFAULT_CAPACITY_MODE = CapacityMode.OBSERVED_CALENDAR (line 117).

Two modes:

observed_calendar (the default, is_default=True in CONFIG_GRID, strict_priority__observed_calendar): "The number of inspections Chicago actually performed on that date, read from the recommendation universe's inspection_date column. Measured." (CapacityMode.OBSERVED_CALENDAR docstring, lines 102–104). The operating-day set and its per-day slot count are computed by observed_calendar_from_dates() in src/sentinel/scheduling/horizon.py (lines 136–146): one pass counting inspections per date from the fold's real historical data, sorted ascending. CALENDAR_IS_OBSERVED (definitions.py lines 142–147) states explicitly: "No working-week rule, no holiday calendar and no generated date appears anywhere in this component; a day is an operating day because Chicago inspected on it."

Function that computes the horizon calendar/slots: build_horizon() in src/sentinel/scheduling/horizon.py (lines 46–113). It takes the fold's precomputed calendar: Sequence[tuple[date, int]] (built once per fold by observed_calendars() in inputs.py, called from build.py line 325) and, for observed_calendar mode, assigns n_slots = observed (the real count) per day (lines 94–98).

2. Horizon calculation
Function: horizon_days(k, median_daily_capacity) in src/sentinel/scheduling/definitions.py (lines 155–168):


return -(-k // median_daily_capacity)   # ceil(k / median_daily_capacity)
Documented as HORIZON_RULE (lines 129–137): "horizon_days = ceil(k / test_median_daily_capacity), taken as a prefix of the fold's own observed operating days. The horizon is identical in both capacity modes; only the per-day slot count differs."

k_levels for this manifest (from data/processed/scheduling/manifest_inspection_schedule_20260826T131416Z.json, key k_levels): ["k_pct_01","k_pct_05","k_pct_10","k_1_day","k_1_week"]. primary_k_level = "k_1_day" (also confirmed in src/sentinel/policy/definitions.py line 105: PRIMARY_K_LEVEL = "k_1_day").

By construction (evaluation.simulate.capacity_k_values, referenced in the horizon.py module docstring lines 3–8), k_1_day is set equal to the window's own measured median daily capacity — i.e., k == median_daily_capacity for that fold at that k level. That is exactly what I verified from schedule_summary_20260826T131416Z.parquet:

quarterly-2026Q2    28  28                       1              2026-04-01      2026-04-01    28
So horizon_days = ceil(28/28) = 1. Yes — it is mathematically expected: k_1_day is defined as "one day's worth of capacity," so ceil(k/median_daily) = 1 for every fold at this k level (I confirmed all 18 fold rows for k_1_day in the summary table give horizon_days == 1, every single one). A schedule built for k_1_day will, by definition, always span exactly one calendar day — the first operating day in the fold's observed calendar.

4. Bug or intended behavior?
Both halves of the determination hold:

Mathematically correct: k_1_day is defined (by the inherited evaluation.simulate.capacity_k_values rule and HORIZON_RULE) to mean "as much capacity as the window's own median day holds." horizon_days(k, median_daily_capacity) = ceil(k/median_daily_capacity) = 1 whenever k == median_daily_capacity, which is what k_1_day is built to be. Verified directly from schedule_summary_20260826T131416Z.parquet: for fold quarterly-2026Q2, k=28, median_daily_capacity=28, horizon_days=1, and both strict_priority__observed_calendar and strict_priority__flat_median configs (all 7 policies) independently produce n_scheduled=28, n_backlog=0 on the single date 2026-04-01. place() in src/sentinel/scheduling/allocation.py (lines 65–123) is a deterministic day-by-day, rank-order fill; with a 1-day horizon holding 28 slots and a queue of exactly 28 approved rows, all 28 necessarily land on that one day — there is no branch anywhere in build_horizon/place/build.py that could spread them across additional days, and BLOCKED in definitions.py (lines 668–684) explicitly forbids "raising capacity, extending a horizon or adding an operating day."
UI/copy problem: the "Planning period: Apr–Jun 2026" banner is generated purely from foldLabel(scope.fold_id) (the fold's 3-month evaluation window), with zero reference to the schedule's actual horizon_start_date/horizon_end_date/horizon_days (which live only in the deeply-nested schedule_summary technical table). The banner text and its surrounding hint text ("This view shows Sentinel's completed planning run for this period...") strongly imply the schedule covers that period, when in fact only the fold/evaluation window does. That is the semantic mismatch, and it is exactly where the "all on one day" surprise originates for a user.
No code bug found: I found no incorrect date being assigned, no off-by-one, no wrong-fold lookup, no capacity being mis-measured. 2026-04-01 is genuinely the first observed-calendar operating day (or first flat_median horizon day) of fold quarterly-2026Q2, and 28 genuinely is that day's real/assumed capacity. The scheduling validator (checks.horizon_is_ordered_contiguous_and_real, checks.capacity_matches_the_declared_mode, etc., all passed: true in the manifest's checks list) independently confirms the horizon and capacity are internally consistent with the frozen rules.
Compounding factor: This isn't a rare edge case a user would have to go out of their way to hit. useDefaultScope (frontend/src/hooks/useDefaultScope.ts, lines 44–59) auto-selects latestQuarterlyFold() (→ quarterly-2026Q2, since it's the last entry in FOLD_TABLE's quarterly rows) and policyManifest.primary_k_level (→ "k_1_day", confirmed in the manifest JSON) for any first-time visitor with no scope in the URL. So the exact anomalous-looking case is the out-of-the-box default experience on OverviewPage, SchedulePage, and TodayPage alike.

2.4 ML target construction — exact mechanics
Source: src/sentinel/target/construct.py, models.py, violations.py, build.py.

Unit of prediction: an (establishment, inspection_date) pair — "one scheduling decision" (models.py:141-147, construct.py:161-172), not a single inspection row.

Eligibility gates (evaluated in fixed order, construct.py::classify_inspection, lines 98-152):

INELIGIBLE_ERA — inspection_date < CODE_ERA_START ("2018-07-01"). This is the 2018 Chicago food-code cutover from Critical/Serious to Priority/Priority Foundation/Core terminology, verified in code comments as a clean cutover ("June 2018 has 0 rows using the new terminology... July 2018 has 761 and 0", models.py:25-29).
INELIGIBLE_TYPE — inspection type (uppercased/whitespace-collapsed) must equal "CANVASS" exactly (CANVASS_TYPE, models.py:52). "Canvass Re-Inspection" is explicitly excluded (construct.py::is_canvass docstring, 16,998 code-era rows) "because a re-inspection exists only because an earlier inspection failed... would condition the target on past failure and inflate the base rate."
INELIGIBLE_RESULT — results must be in INSPECTED_RESULTS = {"Pass", "Pass w/ Conditions", "Fail"} (models.py:40). Excludes "Out of Business", "No Entry", "Not Ready", "Business Not Located" (no inspection took place).
UNKNOWN_VIOLATIONS — if violations text is empty AND results != "Pass", the row is excluded rather than guessed at (a Fail/Pass w/ Conditions result with no violation text is self-contradictory and is not resolved by assumption).
Positive class definition: has_priority_violation() — true if any parsed violation entry in the day's canvass(es) has severity PRIORITY or PRIORITY_FOUNDATION (violations.py::classify, models.py::Severity.is_priority). This is exactly Priority/Priority Foundation violations, as the prompt describes, confirmed by regex markers PRIORITY\s+FOUNDATION and PRIORITY (checked in that order because Foundation contains the bare word) after excluding narrative false positives (grace-period boilerplate, future-tense "WILL BE ISSUED" warnings, explicit "NO PRIORITY" negations — violations.py::NARRATIVE_PATTERNS, lines 51-61). Classification is marker-based regex, not the results column and not an LLM/ML classifier — construct.py docstring explicitly states results are read only for eligibility, "not to decide the label," to avoid circularity.

Label construction is a pure function of violation text alone — no code-era severity heuristics beyond the regex markers, and no municipal-code (7-38-xxx) requirement (deliberately, because 21,281 entries carry a PRIORITY marker with no code — violations.py:17-21).

Same-day collapse: multiple eligible canvasses on the same establishment-date are OR'd together (construct.py::collapse_same_day) — target=1 if any contributing canvass was positive. Documented as load-bearing: "582 establishment-dates carry more than one eligible canvass and 160 of those disagree on the outcome" (line 165-166).

2018 adoption-phase flag (not exclusion): rows in 2018-07-01..2018-12-31 are tagged CodeEraPhase.ADOPTION rather than dropped, because the positive rate then was 87.4% vs 38.9% later (a 90-day grace period was in effect) — models.py:31-34, construct.py::code_era_phase. This is a flag surfaced to Component 5 (evaluation) to decide whether to hold out, not an automatic exclusion baked into Component 3.

Determinism: label is a pure function of violation text; same-day collapse orders by numeric inspection_id; output rows sorted by (establishment_id, inspection_date, inspection_id) — three properties the module states are individually asserted by tests (build.py:6-12).

TARGET_DEFINITION_VERSION = "v1" is stamped on every output row and bumped whenever any of the above rules change (models.py:18-23).

2.5 As-of leakage protection
Core as-of function: src/sentinel/features/historical.py::compute_features() (called from features/build.py::build_features), which executes a single DuckDB range join:


FROM targets t
LEFT JOIN history h
  ON  h.establishment_id = t.establishment_id
  AND h.inspection_date  <  t.inspection_date   -- THE temporal boundary
(historical.py:224-227, comment literally labels this line "THE temporal boundary"). The join uses strict <, not <=, because inspection_date carries no time component and 43 same-day canvass re-inspections were measured to have happened after the canvass they logically follow (historical.py:23-26). It is a single GROUP BY over one range join rather than a whole-history groupby + merge (explicitly called out as "the classic all-history bug" it avoids, line 18-20) and rather than a row-by-row Python loop (would be O(N×M) at 57,727 targets × 314,245 inspections).

Cross-component consistency guard against label/feature drift: historical.py::priority_flags() re-uses sentinel.target.violations.parse_violations (Component 3's own parser) rather than re-implementing a LIKE '%PRIORITY%' SQL approximation, specifically so "priority" cannot mean something different in a feature than in the label (historical.py:31-35, 62-76).

Dedicated leakage test file: tests/test_features_leakage.py (found via grep -rniE "leak|as_of" tests). File-level docstring: "This file exists so that reintroducing future information into a feature is impossible without a test failing... Each test follows the same shape: build features, perturb the future or the present, rebuild, and assert an earlier row did not move" (lines 1-11). Concrete tests, with citations:

tests/test_features_leakage.py:102-118 — test_appending_a_future_inspection_changes_nothing: appends a 2025 record; asserts the 2020 target row's feature vector is byte-identical before/after.
tests/test_features_leakage.py:121-141 — test_appending_many_future_inspections_changes_nothing: same with 5 future records.
tests/test_features_leakage.py:147-173 — test_changing_a_future_outcome_changes_nothing: flips a 2025 record from clean-pass to priority-fail; asserts no change to an earlier row.
tests/test_features_leakage.py:179-207 — test_target_inspection_never_enters_its_own_features: the inspection being labeled is itself given a priority violation; asserts prior_canvass_priority_count == 0 and days_since_last_canvass != 0 (i.e., its own row cannot count itself as history).
tests/test_features_leakage.py:210-241 — test_a_positive_target_does_not_inflate_its_own_history: identical inputs except the outcome label; asserts full feature-column equality.
tests/test_features_leakage.py:247-281 — test_same_day_records_are_excluded: a same-day complaint and same-day canvass re-inspection must not enter history (prior_complaint_count == 0, prior_reinspection_count == 0).
tests/test_features_leakage.py:284-300 — test_a_record_one_day_earlier_is_included: boundary is exclusive at day 0, inclusive at day −1 (days_since_any_inspection == 1).

Equivalent leakage-specific test files exist at every downstream stage (test_modeling_leakage.py, test_boosting_leakage.py, test_neural_leakage.py, test_calibration_leakage.py, test_explain_leakage.py, test_fairness_leakage.py, test_evaluation_leakage.py, test_policy_leakage.py), indicating leakage testing is a systematic pattern across the whole pipeline, not unique to Component 4 — though only test_features_leakage.py was read in full for this audit; the others were confirmed to exist by filename only.

Verdict: community_area and zip are used as raw categorical embeddings only in the experimental Component-8 neural layer; they are absent from the production feature table (Component 4) and from every boosting/baseline model (Components 6-7). No KDE or distance-based feature exists anywhere.

1. CANDIDATE POOL CONSTRUCTION ("1,638 considered")
1.1 Where the eligibility/inclusion filters actually live
The "universe considered" for a policy run is not filtered inside src/sentinel/policy/. The candidate pool is fixed far upstream, at Component 3 (target construction) and Component 4/5 (features/folds), and Component 13 simply consumes whatever rows those components already decided are labellable decision points. Concretely:

Canvass-only filter, exclusion of re-inspections/complaints/license inspections: src/sentinel/target/construct.py

is_canvass() (line 62-69): normalize_inspection_type(raw) == CANVASS_TYPE. Docstring: "Excludes Canvass Re-Inspection (16,998 code-era rows). A re-inspection exists only because an earlier inspection failed, so including it would condition the target on past failure and inflate the base rate."
classify_inspection() (lines 98-152): gate order is (1) in_code_era (>= 2018-07-01), (2) is_canvass, (3) results in INSPECTED_RESULTS (excludes "Out of Business", "No Entry", "Not Ready", "Business Not Located"), (4) has parseable violation text. Anything failing any gate gets TargetStatus = INELIGIBLE_ERA / INELIGIBLE_TYPE / INELIGIBLE_RESULT / UNKNOWN_VIOLATIONS and target=None — i.e., it is excluded from the labellable/scorable universe entirely (complaint inspections, license inspections, and re-inspections are all filtered out here as "not canvass").
This means: complaint and license inspections never even become target_inspection_id rows; canvass re-inspections are explicitly excluded by name.
Establishment-date grain, one row per decision point (not per establishment overall): build_target_rows() (lines 227-262) and collapse_same_day() (lines 161-202). Eligible canvasses are grouped by (establishment_id, inspection_date) and collapsed to one row per establishment-date (target = OR over that day's canvasses). So target_inspection_id identifies an establishment-date decision point, not a raw inspection_id and not an establishment. An establishment CAN appear more than once in the universe if it had more than one canvass on different dates that both fall inside the same fold's test window (multiple decision points across the study period). PolicyWindow.__post_init__ (src/sentinel/policy/models.py lines 80-93) only asserts target_inspection_id uniqueness, not establishment_id uniqueness — so the policy layer does not guarantee one row per establishment; "establishments considered" in the UI is actually a count of scored decision points (establishment-dates), which can slightly overcount unique establishments. This is a real UI-vs-code semantic gap worth flagging (see §6).

"Minimum feature completeness" / no missing-score tolerance: src/sentinel/policy/inputs.py, build_window() (lines 242-282). The join between the feature-table test window and the calibrated predictions is an inner join, then explicitly checked: if scored.height != window.height: raise PolicyInputError(...) (lines 262-267) — "The policy layer never imputes a missing score." So a row must have both a Component 4 feature row and a Component 9 calibrated score to enter the universe; any row for which a score is missing is rejected with a hard error, not silently dropped.

Recency exclusion ("already inspected recently"): NOT a separate filter in Component 13. The only "already inspected recently" style constraint present is upstream, structural: the collapse-to-one-row-per-establishment-date logic and the fold/window construction (src/sentinel/evaluation/folds.py, window_frame() lines 248-260, and assign_split) which partitions rows into train/calibration/test by date — a given fold's "test window" (the candidate pool for a scope) is simply every eligible canvass-decision-point whose reference date (rd) falls in that fold's test period, sorted by (rd, target_inspection_id). There is no additional "don't recommend an establishment inspected N days ago" rule anywhere in src/sentinel/policy/.

2. SELECTION LOGIC ("28 selected")
2.1 How k becomes an actual count
k_name (e.g. k_1_day) is resolved to an integer k entirely outside the allocator, in sentinel.evaluation.simulate.capacity_k_values() (src/sentinel/evaluation/simulate.py:420-439):


"k_1_day": median_daily,
"k_1_week": median_daily * 5,
"k_1_month": median_daily * 21,
"k_pct_01"/"k_pct_05"/"k_pct_10"/"k_pct_25"/"k_pct_50": rounded shares of window.n
median_daily comes from sentinel.policy.inputs.median_daily_capacity() (inputs.py:118-126), which calls sentinel.evaluation.folds.fold_stats() (folds.py:213-245) — the median number of inspections Chicago actually performed on a day inside that fold's test window (test_median_daily_capacity, floored at 1). This is exactly where "28" comes from: k_1_day is not a fixed constant anywhere; it is a per-fold empirical measurement of real historical daily throughput. K_LEVELS (the set of capacity levels a policy is reported at) is imported into src/sentinel/policy/definitions.py:100 from sentinel.fairness.definitions.K_LEVELS = ("k_pct_01", "k_pct_05", "k_pct_10", "k_1_day", "k_1_week") (src/sentinel/fairness/definitions.py:309), and PRIMARY_K_LEVEL = "k_1_day" (definitions.py:105) is the operating point the summary/UI leads with — consistent with the app showing a k_1_day-style scope by default.

allocate() (src/sentinel/policy/allocation.py:95-158) then does capacity = min(k, window.n) (line 107) — so if the fold's k_1_day value is 28 and the window has ≥28 rows, exactly 28 slots are selected: Allocation.n_selected = n_risk + n_reserve (models.py:139-141), and the allocator's contract (checked by validate.selected_counts_equal_capacity, validate.py:128-) forces n_selected == k on every cell.

2.2 Reserve/coverage mechanism and its effect on the selected count
ReserveMechanism enum (definitions.py:121-145): NONE (no reserve, pure risk order is the queue), FLOOR (guarantee at least share*k of the queue is coverage-eligible; does nothing if risk ranking already clears it — "inert" is expected/measured, not an error), FORCED (spend share*k slots on eligible rows the risk ranking did not already select, regardless of whether risk already covers them).
reserve_target() (allocation.py:71-83): int(spec.reserve_share * k) — truncated, never rounded up, so a small reserve_share at a small k can floor to 0 (reserve_inert property, models.py:143-151).
Inside allocate() (allocation.py:95-158):
cumulative = _eligible_prefix_counts(window, order) (line 112) — counts how many coverage-eligible rows are already inside each risk-rank prefix.
eligible_in_top_k = cumulative[capacity] (line 113) — how many eligible rows the pure risk order already delivers within the top-k.
For FLOOR: wanted = max(0, target - eligible_in_top_k) — only the shortfall.
For FORCED: wanted = target unconditionally.
granted is then solved by walking up from 0 while enough eligible rows remain outside the retained risk block (lines 126-132) — this is what turns a "reserve share" into an actual number of reserved slots, and it can land below the target if too few eligible establishments are left.
risk_indices = order[: capacity - granted] — the risk block shrinks by exactly the granted reserve size; reserve_indices are filled from eligible rows the risk block didn't already take. Total selected is always exactly capacity (== k) — the reserve mechanism only changes who fills the k slots, never how many.
decide() (allocation.py:161-197) assigns decision_mechanism/decision_reason/final_policy_rank per row: risk block ranked 1..n_risk first, reserve block ranked n_risk+1..k next; everything else is not_selected with reason not_selected_capacity_exhausted (outranked, ineligible) or not_selected_reserve_exhausted (eligible but reserve didn't reach it).
2.3 Concrete trace of why k_1_day → 28 selected
fold_stats() measures test_median_daily_capacity for the fold = e.g. 28 (an empirical median of Chicago's actual daily canvass counts in that period).
capacity_k_values() sets k_1_day = 28.
build._capacities() stores capacities[fold_id]["k_1_day"] = 28.
build._allocations() calls allocate(window, spec, k_name="k_1_day", k=28).
allocate() sets capacity = min(28, window.n) — assuming window.n (e.g. 1,638) ≥ 28, capacity = 28.
For policy_id="pure_risk" (mechanism=NONE), wanted=0, so all 28 slots come from risk_indices (top 28 by calibrated score). For a coverage policy (e.g. coverage_floor_population_share, reserve_share=0.10), reserve_target = int(0.10*28) = 2; if the risk-ranked top-26 already contains ≥2 eligible rows the floor is inert (0 granted); otherwise up to 2 reserve slots are added and the risk block shrinks to 26.
Either way Allocation.n_selected == 28 by construction, and is_selected=True is written on exactly 28 of the ~1,638 candidate rows for that cell in _recommendation_frame() (build.py:261-315, "is_selected": [rank is not None for rank in ranks]).
validate.selected_counts_equal_capacity (validate.py:128-) asserts selected == k for every (policy,model,fold,k_name) cell at error severity — a run cannot ship a mismatched count.

4.2 Overrides (apply_overrides)
sentinel.policy.governance.apply_overrides() (governance.py:142-241), invoked from build._production_pass() (build.py:727-738) only when an override file is supplied:

Overrides addressed to the current (policy_id, fold_id, k_name) cell are filtered, then applied in override_id order (not file order) — deterministic regardless of file serialization (line 177).
FORCE_INCLUDE: if already selected → no_op_already_selected; else finds _lowest_standing_risk() (lines 243-255) — the risk-selected row with the worst final_policy_rank still standing — and displaces it (selected[victim]=False, selected[position]=True), records displaced_target_inspection_id. Never raids the reserve block — only risk-block rows can be displaced. If nothing is standing to displace, raises GovernanceError (would raise capacity, which the simulation never does).
FORCE_EXCLUDE: if not selected → no_op_not_selected; else selected[position]=False with no backfill — the freed slot is left empty; a queue can therefore end up with fewer than k inspections after overrides (documented deliberately: "the policy does not quietly promote the next one").

parse_overrides() (governance.py:96-139) enforces all-or-nothing validation at the boundary: every Override field required and non-blank, action must be a known OverrideAction, and duplicate override_ids refuse the whole file.

5.3 Resolution actions — IMPLEMENTED status and exact behavior
All four ReviewResolutionAction values (review/definitions.py:144-166) are IMPLEMENTED in src/sentinel/review/resolution.py:

acknowledge: No pointer field required/allowed (POINTER_FIELD_FOR_ACTION[ACKNOWLEDGE] = None). In apply_resolutions() (resolution.py:90-144) it does exactly the same thing every resolution does structurally: if the case is RESOLVED already → no_op_already_resolved; else flips final_status[key] = ReviewCaseStatus.RESOLVED and records outcome = applied. It performs no other action — it only marks the case resolved. It does not touch any Component 13/14 artifact.
refer_to_override: Requires non-blank referenced_override_id (enforced in parse_resolutions(), lines 64-77); functionally identical to acknowledge in apply_resolutions() — flips the case to RESOLVED and records the pointer in the log row. It does not create, look up, validate existence of, or apply the referenced override — POINTER_MAY_FORWARD_REFERENCE = True (definitions.py:215) — the override may not even exist yet; only the review_advisories table checks it, as an advisory (never a hard failure) per docs/data_contracts/human_review.md line 147: "a pointer that does not yet resolve to a committed override or adjustment."
refer_to_adjustment: Same as above, but for referenced_adjustment_id and Component 14's adjustment contract.
escalate: Requires no pointer field (POINTER_FIELD_FOR_ACTION[ESCALATE] = None), but the model carries an optional escalation_note: str | None (review/models.py:108) — "free text, only meaningful for escalate" per the data contract. Escalate does literally nothing beyond acknowledge in apply_resolutions() — it flips the case to RESOLVED, records outcome=applied, and stores whatever free-text note the reviewer typed. There is no downstream consumer of escalate that pages anyone, opens a ticket, or takes any programmatic follow-up action — it is purely a recorded annotation. Confirms your suspicion: escalate does not do anything beyond recording a note.
REVIEW_CANNOT (review/definitions.py:204-210) states this explicitly as a design constraint: "a review resolution changes only the review case's own status... Referring a case to override or adjustment records the human's stated intent as a pointer; it never creates the override or adjustment record itself."

All four actions are also enforced to be lexically disjoint from OverrideAction and AdjustmentAction verbs (_guard_registry(), review/definitions.py:274-341), and none may contain the substring "defer" (to avoid confusion with Component 14's ScheduleStatus.DEFERRED).

A5. Staged-vs-committed write model — CONFIRMED / IMPLEMENTED, with CLI apply points verified
src/sentinel/api/services/staging_service.py::StagingService (full file read):

append() (line 51) writes one JSON line to an append-only .jsonl file per contract kind (_KIND_CONFIG, lines 28–33: override → policy/overrides_pending.jsonl, adjustment → scheduling/adjustments_pending.jsonl, execution_event → scheduling/execution_events_pending.jsonl, review_resolution → review/resolutions_pending.jsonl).

2. TRAINING / VALIDATION STRATEGY
VERIFIED BY CODE — rolling-origin / temporal backtest, no random k-fold anywhere in this scope.

src/sentinel/evaluation/folds.py implements an expanding-window, rolling-origin quarterly backtest:

quarterly_folds() builds folds as: train [anchor .. calibration_start-1] → calibration [quarter Q] → test [quarter Q+1], expanding the training window forward one quarter each fold. Anchor = CODE_ERA_ANCHOR = date(2018,7,1), MIN_TRAIN_QUARTERS = 14.
A second, deliberately separate fold set, covid_shift_fold(), trains pre-COVID (train_end=2020-02-29) and tests through the 2020 disruption (test 2020-06-01..2021-12-31) — purpose stated in the docstring: to test "does the ranking survive an operational regime change," not average performance.
assign_split() labels every row train/calibration/test/outside via chained date comparisons — a row cannot receive two labels, so overlap is structurally impossible.
Calibration window sits strictly between train and test and is never merged into either (enforced comment in the module docstring and honored in the actual FoldSpec construction).

4. CALIBRATION
VERIFIED BY CODE — both Platt scaling and isotonic regression are implemented, with a coded selection rule, and the actual production candidate is Platt.

src/sentinel/calibration/train.py: fit_platt() — "Platt scaling: a logistic regression of the label on logit(p)... unpenalised (C=1e10)" — and fit_isotonic() using sklearn.isotonic.IsotonicRegression.
Selection rule: select_method() (train.py ~line 251) picks isotonic only if it beats Platt by more than a margin on mean inner-select log-loss; TIE_PREFERENCE = Method.PLATT (src/sentinel/calibration/definitions.py:209) — ties and near-ties go to Platt because it is "strictly monotone where isotonic is only weakly monotone" (isotonic plateaus can perturb rank order / top-k membership).
Actual selection in the live data: I read data/processed/calibration/calibrator_parameters_20260824T163608Z.parquet directly. For model_name == "xgboost", both methods are fit for every one of the 18 folds, but the was_selected == True rows are 100% Platt across all 18 folds (17 quarterly + covid_shift) — matching the production model name xgboost_platt end-to-end.
The calibrated score is explicitly declared to be P(target = 1), and the target — per the folds manifest's own inherited_limitations field — is "that a Priority violation was cited, not that an establishment was unsafe." So the calibrated score means P(a Priority/Priority Foundation violation is cited on this inspection), per the labeled target, not a broader safety concept.
Honesty caveat present in the manifest itself: "Component 9: probabilities are calibrated in the quarterly mean, not in any single quarter, and calibration made ECE worse on 16 of 85 quarterly cells." This is a real, coded finding surfaced in inherited_limitations — calibration does not uniformly improve every fold/model cell.
Thresholding: explicitly not used. The policy manifest states: "capacity_semantics": "capacity is a rank position derived from the window's measured median daily inspection rate. No policy in this component uses a probability threshold, and there is no flag to add one", and lists as a blocked action: "introducing a probability threshold (Component 12's THRESHOLD_POLICY)". Ranking downstream (src/sentinel/policy/allocation.py:top_k_indices(), model_ranks()) operates purely on window.scores (the calibrated score) sorted/ranked — it is used purely as a ranking score, capacity-constrained by observed daily inspection volume (k), never gated by a probability cutoff.
5. MODEL ARTIFACT + INFERENCE PATH
VERIFIED BY CODE — there is no persisted, loadable model artifact (no pickle/joblib .pkl/.joblib file anywhere in the training code); the "artifact" is the prediction table, not a serialized model.

I grepped src/sentinel/modeling, boosting, neural for joblib|pickle|\.pkl|dump( — the only hits are unrelated (booster.get_dump(), an XGBoost text-dump introspection call, not model serialization). Models are refit in-process, per fold, on every training run, immediately scored against that same fold's test window, and then discarded; only the resulting numeric predictions are written to disk.
Full pipeline as coded in src/sentinel/cli.py subcommands (no single unified "predict" command exists; each stage is separate):
sentinel train-boosting → for each BoostingSpec × fold, estimator_params() builds the frozen tuned hyperparameters (src/sentinel/boosting/definitions.py), the estimator is fit (src/sentinel/boosting/train.py) on [train_start, calibration-1], producing a FittedBooster, then src/sentinel/boosting/predict.py:50 calls fitted.estimator.predict_proba(matrix) on the fold's test window, and results are written to boosted_predictions_*.parquet with columns including raw score.
sentinel calibrate → src/sentinel/calibration/build.py reads the base-model prediction artifacts, regenerates the base score in-fold as a control (checked bit-identical against the committed artifact — base_scores_reproduce_the_committed_artifact, BIT-IDENTICAL/MISMATCH gate), fits Platt/isotonic on the calibration window, applies it (src/sentinel/calibration/predict.py:apply) to the test window, and writes calibrated_predictions_*.parquet with both base_score (raw) and score (calibrated) columns (src/sentinel/calibration/build.py:553-574).
sentinel decide (src/sentinel/policy/build.py) reads calibrated_predictions_*.parquet + evaluation metrics/sensitivity/simulation artifacts, runs the coded selection rule (src/sentinel/policy/definitions.py), and writes inspection_recommendations_*.parquet, again carrying both base_score and score columns straight through (src/sentinel/policy/build.py:300-301: "base_score": list(window.base_scores), "score": list(window.scores)).
sentinel serve (API) — src/sentinel/api/services/policy_service.py:_recommendations_frame() simply does resolve_latest(..., prefix="inspection_recommendations") and reads the already-materialized Parquet file. There is no live model inference at API request time — the API is a read layer over a pre-computed batch table.
Which column is which, verified in src/sentinel/api/schemas/policy.py (RecommendationOut) alongside the writer code:

base_score: float — the raw/uncalibrated model output (e.g., XGBoost's own predict_proba sigmoid output before Platt scaling), regenerated in calibration/build.py and checked bit-identical against the original training-time artifact.
score: float — the Platt-calibrated probability (for the production model xgboost_platt), produced by src/sentinel/calibration/predict.py:_apply_platt and is the value actually used for ranking (src/sentinel/policy/allocation.py:top_k_indices(window.scores, ...), model_ranks(window)).
So: score = calibrated, base_score = raw model output kept only for provenance/audit, not used for ranking.

6. WHAT DOES THE FINAL SCORE ACTUALLY REPRESENT?
Labeled as, and structurally treated as, a calibrated probability — with real, coded evidence of imperfect calibration, and it is used purely as a ranking score, never thresholded.

Code-level intent is unambiguous: the neural predict module states outright "P(target = 1)"; the boosted manifest field is literally named probability_semantics; XGBoost's objective is binary:logistic, LightGBM's is binary; the calibration layer's entire purpose (Platt/isotonic) is to map raw scores to well-calibrated probabilities, verified against ECE/Brier/log-loss on held-out quarters.
Confidence this is a genuine calibrated probability, not just a label: moderate-to-high, but explicitly and honestly bounded by the codebase itself. Evidence for genuineness:
ECE for the production model is measured and reasonably low (mean 0.0474 across 17 real quarterly folds — computed above from live data, not asserted).
The calibration build pipeline actually verifies its own base-score regeneration is bit-identical to the training-time artifact before trusting it (a real leakage/consistency guard, not just a comment).
A genuine per-fold Platt vs. isotonic selection on held-out log-loss was run and its result is stored per fold (not hardcoded) — I confirmed the winner varies row-by-fit but the network Platt was chosen for the deployed model in every one of the 18 folds.
Evidence for caution (found in the artifacts themselves, not invented for balance):
The manifest's own inherited_limitations states calibration made ECE worse on 16 of 85 quarterly (model×fold) cells — i.e., calibration is not uniformly an improvement; it is monitored and imperfect, and this is surfaced rather than hidden.
The target itself is that a Priority/Priority Foundation violation was cited (an inspector's finding), not an independently verified ground-truth safety state — so "P(target=1)" is a well-defined probability of a labeling event, not of "the establishment is genuinely unsafe." This is explicit in the folds manifest: "the target is that a Priority violation was *cited*, not that an establishment was unsafe."
Calibration is reported as accurate "in the quarterly mean, not in any single quarter" — i.e., aggregate calibration is good, but any individual quarter's calibration can be off.
Downstream use is purely as a ranking score: the policy layer explicitly blocks introducing any probability threshold (blocked list in the recommendations manifest names this literally), and capacity/k is derived from observed daily inspection throughput, not from a probability cutoff. So regardless of how well-calibrated it is, the system architecture treats the value primarily as an ordering signal for a capacity-constrained top-k queue — calibration exists to support fair comparison across models/folds and to make base_score meaningfully comparable to a probability scale, not to drive a go/no-go decision rule.
Bottom line: VERIFIED-BY-CODE-OR-DATA that the score is architecturally and numerically a calibrated probability (Platt-scaled XGBoost output) with measured, non-trivial calibration error (ECE ≈ 0.047, Brier ≈ 0.235) reported transparently including known failure modes; VERIFIED-BY-CODE that it is consumed purely as a rank-ordering value with no threshold anywhere in the decision path.

Executive Summary
Sentinel is a real, working, temporally-disciplined ML pipeline over exactly one real dataset — Chicago's Socrata food-inspections feed (4ijn-s7e5) — with no fabricated or simulated ground truth anywhere. The as-of feature boundary, the temporal (never random) fold structure, the label-construction logic, and the leakage tests are all genuinely implemented and enforced by code, not just claimed in docs. Calibration, model selection, and policy allocation are real, numerically grounded, and self-critical (the codebase's own manifests state their own limitations, e.g., "calibration made ECE worse on 16 of 85 cells").

However, three large categories of the original build spec were never implemented, and the code says so explicitly:

No spatial/geographic feature or routing capability exists anywhere. Coordinates are used transiently during entity resolution and then discarded before any downstream table. OR-Tools is not a dependency. No distance matrix, no VRP, no route ever runs.
No inspector data of any kind exists, because the source dataset structurally contains none (not a modeling choice — there is no person-identifying column in the raw feed at all). This blocks inspector-effect marginalization, routing, and any real operational-resource modeling.
No statutory mandate / CDPH risk-category / overdue-inspection enforcement exists anywhere in the policy layer, despite being the central "hard constraint" concept in the original spec. Selection is risk-rank + a coverage/reserve mechanism only.
The "Apr–Jun 2026 planning period, but everything is scheduled on April 1" anomaly you flagged is not a bug — it is the mathematically correct behavior of k_1_day (defined as exactly one day's worth of real historical capacity) colliding with a UI banner that conflates "the fold being evaluated" (3 months) with "the schedule's actual horizon" (which can be 1 day). This is the single highest-value, cheapest fix available before any redesign.

PART 4 — Model Audit
Model types trained, all real: logistic regression (baseline + CDPH-2015 approximation), XGBoost, LightGBM, and an experimental neural net with categorical embeddings (chain/facility-type/community-area/zip).

Production model, verified from the live manifest: xgboost_platt (XGBoost + Platt-scaled calibration). Selection is a coded, auditable tie-break: PR-AUC is statistically indistinguishable across all four admissible candidates (spread ≈0.002); the deciding axis is ECE (lower is better). A fifth model, xgboost_chain_embeddings, actually scores better on both PR-AUC and ECE but is coded as refused — reason recorded verbatim in the manifest: "a model whose recommendations cannot be explained to the inspector acting on them is not a deployment candidate, whatever it scores" (ties to Component 11 explainability support).

Validation strategy — rolling-origin, never random. evaluation/folds.py builds an expanding-window quarterly backtest (train → calibration → test, strictly non-overlapping) plus one separate covid-shift stress fold. 18 real folds exist in the live data (17 quarterly + 1 covid_shift); the trailing incomplete quarter (2026Q3) is explicitly excluded rather than padded. No KFold/train_test_split/random shuffle exists anywhere in the model-training code.

Actual latest numbers (read directly from evaluation_metrics_*.parquet, mean across 17 quarterly folds, production model xgboost_platt):

Metric	Value
PR-AUC	0.534
ROC-AUC	0.619
ECE	0.047
Brier	0.235
Precision@k (k_1_day)	0.631
For comparison, random=0.438 PR-AUC, business_as_usual=0.435 — so the model beats naive baselines, but only modestly, and the four real candidate models cluster within noise of each other.

Calibration — both Platt and isotonic implemented; Platt won on every one of the 18 folds (tie-break rule explicitly favors Platt's strict monotonicity). Honest self-reported caveat found in the live manifest: calibration made ECE worse on 16 of 85 quarterly (model×fold) cells — this is surfaced, not hidden.

No thresholding anywhere. The policy manifest explicitly lists "introducing a probability threshold" as a blocked action. The score is used purely as a rank-ordering value under a capacity constraint.

No persisted model artifact. There is no .pkl/.joblib file anywhere — models are refit in-process per fold, scored immediately, then discarded; only the resulting prediction table is written to disk. The API layer performs zero live inference — it is a pure read-through of pre-computed batch Parquet.

base_score vs score: base_score = raw uncalibrated model output (kept for audit only); score = Platt-calibrated probability, the value actually used for ranking.

PART 5 — Candidate Pool Audit ("1,638 considered")
Substantive filtering happens upstream in Component 3, not in the policy layer. By the time Component 13 (policy/) sees a row, it has already survived: era≥2018-07-01, canvass-only (excludes complaint/license/re-inspection), results-eligible, parseable violations. Component 13 adds exactly one more hard requirement: a row must have both a Component 4 feature row and a Component 9 calibrated score, or the whole build errors out (no silent imputation).

Grain: one row per establishment-date decision point, not per unique establishment. target_inspection_id uniqueness is enforced; establishment_id uniqueness is not — an establishment with two eligible canvasses in the same fold's test window is counted twice. This is a real semantic gap worth flagging: "establishments considered" in the UI is actually a count of scored decision-points, which can slightly overcount unique establishments.

"1,638" traced exactly: it is window.n — the number of establishment-date rows whose reference date falls in the fold's test window and that cleared the score-join requirement (PolicyWindow.n, exposed verbatim as AllocationOut.n_universe).

"28 selected" traced exactly: k_1_day is not a fixed constant — it equals the fold's own measured median daily historical canvass volume (evaluation.folds.fold_stats() → test_median_daily_capacity). allocate() sets capacity = min(k, window.n); for a coverage-reserve policy, up to reserve_share × k slots (truncated, can floor to 0 — "reserve_inert" is an expected, measured outcome, not an error) are set aside for under-inspected establishments the pure risk order missed; the remainder fills from the risk-ranked order. Total selected is always exactly k by construction, enforced by a validator that errors if it isn't.

PART 6 — Capacity / Scheduling Root-Cause Analysis ("Apr–Jun 2026, but all on April 1")
Verdict: not a code bug. Reproduced with real data (fold_id="quarterly-2026Q2", k_name="k_1_day", k=28):

Capacity is genuinely real historical volume (observed_calendar mode) or a labeled scenario (flat_median), never a fixed/fake number — both independently produced the same result for this scope.
horizon_days = ceil(k / median_daily_capacity). k_1_day is defined to equal that fold's own median daily capacity, so horizon_days = ceil(28/28) = 1 — mathematically forced to be exactly 1 for every fold at this k level (verified across all 18 folds in the summary table).
The greedy day-by-day, rank-order allocator (allocation.py::place()) necessarily puts all 28 approved rows into the single 28-slot day that exists.
The actual defect is a UI copy problem: InspectionPlanSelector.tsx's "Planning period: Apr–Jun 2026" banner is generated purely from foldLabel(scope.fold_id) — the evaluation fold's 3-month window — with zero reference to the schedule's own horizon_start_date/horizon_end_date/horizon_days, which exist only in a buried "Technical details" sub-table. The banner conflates "the window being evaluated" with "the date range this specific plan's schedule spans."
This is the default, out-of-the-box experience for every new user — useDefaultScope auto-selects the latest quarterly fold and the manifest's primary_k_level, which is k_1_day.
No incorrect date assignment, off-by-one, or wrong-fold lookup was found anywhere in horizon.py, allocation.py, build.py, or the API layer.

PART 14 — Critical Questions / Blockers Before Final Architecture
Should "establishments considered" be de-duplicated by establishment_id?
Why it matters: the current count is decision-points, not unique establishments — a small but real accuracy claim.
Supports: trivial to fix, one .unique() call plus a labeling decision.
Recommendation: de-dup and relabel, or explicitly caption it as "scoring opportunities" if the double-count is intentional for some downstream reason.

Is statutory mandate/CDPH-risk-tier enforcement required for v1, given the public dataset has no risk-category field it can be validated against?
Why it matters: it's the spec's core "hard constraint" concept and currently doesn't exist at all.
Supports: the raw feed does carry a risk column (1/2/3) — unused anywhere in the current pipeline. This could plausibly be threaded in as a real feature/constraint without inventing data.
Options: (a) build a real, if simple, CDPH-risk-tier-based mandate layer using the existing risk column; (b) explicitly scope it out of v1 and say so.
Recommendation: (a) — the data to do this honestly already exists and is currently unused.

Is a route/geography layer required for v1, and if so, on what basis?
Why it matters: real coordinates exist but routing needs inspector depot/duration data that doesn't.
Options: (a) skip entirely for v1; (b) build a geography-aware display (map + address) without any solver; (c) build full routing with clearly-labeled user-provided depot/duration config.
Recommendation: (b) as v1, (c) as a later phase, per the user's own instruction not to add agentic/LLM/big new components yet.

What should "operational resources" mean in v1, if inspectors don't exist in the data?
Why it matters: the desired flow explicitly asks a supervisor to "provide or configure the inspection resources available."
Recommendation: a single user-entered capacity override (e.g., "today: N inspectors × M inspections each") layered on top of the existing historical-volume default, clearly labeled as user input, not Chicago fact.

Should the execution-outcome contract capture the actual violation found, closing a real feedback loop?
Why it matters: currently "completed" carries no outcome detail, so the system can never learn from its own operational history.
Recommendation: yes — this is buildable today with real data semantics (reuse the same Priority/Priority-Foundation parser Component 3 already has), and it's high value for any "does the recommendation match reality" story.

Should Human Review get real severity, or should "escalate" be relabeled to match what it actually does?
Why it matters: current UI language ("escalate," "resolve this case") implies more machinery than exists — it's a status flip plus a note.
Recommendation: either build real severity/escalation routing, or rename to avoid overpromising (e.g., "flag for follow-up" instead of "escalate").

PART 15 — Final Architecture Readiness Report
A. What Sentinel already has and should preserve
Single real dataset, zero fabricated ground truth, a genuinely enforced as-of leakage boundary with real CI tests.
Rolling-origin (never random) temporal validation across 18 real folds, honestly reported metrics including where the model is weak.
A real, auditable calibration and model-selection process that explicitly refuses a better-scoring but unexplainable model.
A real capacity/scheduling engine grounded in actual historical Chicago volume.
A real staged-write governance model (override/adjustment/execution/resolution) that never silently mutates a committed artifact.
This session's frontend rebuild (Today page with a real date picker; Needs Attention as a flat task list) — both should be preserved and extended, not redone.
B. What Sentinel has but needs modification
The "Planning period" banner — needs to reflect the schedule's actual horizon, not the evaluation fold.
"Establishments considered" — needs establishment-level de-duplication or a relabel.
Human Review's escalate/refer actions — need either real functionality or honest relabeling.
Execution outcome logging — needs an actual violation-found field to close any real feedback loop.
C. What should likely be removed or redesigned
Nothing needs outright removal — the backend is sound. The Plan Summary page's raw manifest dump and SchedulePage's untranslated "Technical details" tables are the weakest UI surfaces and are candidates for a rebuild pass, consistent with what was already done for Today/Needs Attention.
D. What is missing but can be built using existing real data
A real CDPH-risk-tier mandate layer, using the unused risk column already in the raw feed.
An establishment-identity-aware, geography-displaying (not routing) improvement, using addresses that already exist through Component 2.
A real violation-outcome field on execution events, reusing Component 3's existing parser.
E. What requires user-provided operational configuration
Inspector count/availability for a given planning run.
Any inspector depot/start-location input, if routing is ever built.
Any capacity override beyond the historical-volume default. All of these must be visually and textually distinct from real Chicago data at all times.
F. What cannot honestly be implemented without additional real-world data
Inspector-effect marginalization (no person identifier exists to marginalize over).
Real travel-time/route optimization (no real duration or depot data exists).
Any genuine outcome-based model retraining loop until execution events carry a real outcome field (D, above) and enough volume accumulates.
G. Data integrity, leakage, architectural, and product risks
No leakage risk found in the current pipeline — this was the most heavily-verified area and came back clean across all 7 audits.
Product risk: the fold-window/schedule-horizon conflation (Part 6) is live in the default experience today and is the single most damaging discoverability issue for a first-time user.
Architectural risk: three separate pages (Plan Summary, Today, Needs Attention) surface the identical review-queue counts with no shared source of truth in the frontend — not a data bug, but a maintenance/consistency risk if the two queries ever drift.
Governance risk: "escalate" implying more than it does is a trust risk with a real operational user, not just a cosmetic one.
H. Minimum information still needed before designing the final architecture
A product decision on Part 14's six questions above (dedup counting, mandate scope, geography scope, operational-resource input shape, outcome-field addition, review-severity/escalate honesty).
A decision on whether v1 needs any geography display at all, or whether that's explicitly a later phase.
Confirmation of what "operational resources" should look like as a UI input (a single number? a per-inspector list? a capacity multiplier?) — this is a pure product choice, not something the data can answer.
This audit changed no code. I'm ready to move into architecture design against this document whenever you are — my recommendation is to resolve Part 14's questions first, since every one of them materially changes what the final architecture needs to support.
